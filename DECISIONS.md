# Decisiones y desvíos respecto del PRD

Registro de decisiones tomadas durante la implementación. Cada entrada indica si es un **desvío** del PRD
(requiere aviso al responsable), una **decisión nueva** (el PRD no la cubre) o una **confirmación**.

Convención de idioma: la documentación del proyecto sigue el idioma del PRD (español neutro); el código,
los comentarios, los mensajes de commit y los textos de interfaz están en inglés.

| DEC-1  | 2026-10-18 | Confirmación                | TypeScript 5.8.x                                                     | `npm view typescript version` devuelve 7.0.2, pero el PRD fija 5.8.x (la que usa `@vendure/core` 3.8.0, que declara 5.8.2). Se usa **5.8.3** exacta en todo el repositorio. No es un desvío.                                                                                                                                                                                                                                                                                                                                                                                                                       |
| DEC-2  | 2026-10-18 | Confirmación                | Versiones principales                                                | Contrastadas con el registro de npm el 2026-10-18: `@vendure/*` 3.8.0, `mercadopago` 3.6.1, `next` 16.4.2, `react` 19.3.1, `graphql-request` 7.4.0. Coinciden con la sección 16.                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| DEC-3  | 2026-10-18 | **Desvío**                  | Almacenamiento S3 local                                              | El PRD (16.4, 16.8) usa MinIO en Compose. `minio/minio` y `minio/mc` ya no se pueden descargar (Docker Hub: "pull access denied"; Quay: 401). Se reemplaza por **SeaweedFS** (`chrislusf/seaweedfs`, API S3 en el puerto 8333, publicado en el host como 9000) y `amazon/aws-cli` para crear el bucket. El código sigue sin depender de un proveedor: solo usa `configureS3AssetStorage` con variables `S3_*`.                                                                                                                                                                                                     |
| DEC-4  | 2026-10-18 | Decisión nueva              | Scripts de instalación de npm                                        | Con npm 12 los scripts de instalación están bloqueados salvo que figuren en `allowScripts` del `package.json` raíz. Se aprobaron `bcrypt`, `re2`, `esbuild` y `@apollo/protobufjs` (requeridos por Vendure y Vite). Con npm 11 (imagen `node:24`) el campo se ignora y los scripts corren igual.                                                                                                                                                                                                                                                                                                                   |
| DEC-5  | 2026-10-18 | Decisión nueva              | `csrfPrevention: true`                                               | Vendure 3.8 avisa al arrancar de que el login es vulnerable a CSRF con cookies si no se activa. Se activa. Los frontends llaman desde su servidor con POST JSON, que no se ve afectado; las subidas de archivos y las consultas GET tienen que enviar el encabezado `Apollo-Require-Preflight`.                                                                                                                                                                                                                                                                                                                    |
| DEC-6  | 2026-10-18 | Decisión nueva              | Validación de variables de entorno                                   | Las variables obligatorias se validan con `assertEnv()` al arrancar el proceso, no al importar la configuración, porque `vendure build dashboard` carga la configuración sin entorno (también ocurre en el build de Docker).                                                                                                                                                                                                                                                                                                                                                                                       |
| DEC-7  | 2026-10-18 | Decisión nueva              | Módulos del servidor                                                 | `apps/server` usa `module/moduleResolution: node16` (salida CommonJS, sin `type: module`) en lugar de `commonjs/node`, para que TypeScript respete los `exports` de `@vendure/dashboard`. También `useDefineForClassFields: false` (necesario para decoradores de TypeORM con target ES2022).                                                                                                                                                                                                                                                                                                                      |
| DEC-8  | 2026-10-18 | Confirmación (V10, parcial) | Servidor con `strict`, `UuidIdStrategy`, PostgreSQL 17               | El servidor arranca con `strict: true`, `UuidIdStrategy` y la migración inicial (91 referencias a `uuid`), el worker arranca y expone `/health` en 3020, el dashboard compila y el superadmin inicia sesión por la Admin API (id devuelto con formato UUID). Falta la parte del SDK de Mercado Pago (T2/T4).                                                                                                                                                                                                                                                                                                       |
| DEC-9  | 2026-10-18 | Decisión nueva              | Firma de webhooks: `ts` y `data.id`                                  | La documentación dice que `ts` está en milisegundos, pero su ejemplo (`ts=1704908010`) y el SDK 3.6.1 lo tratan como segundos. La ventana de tolerancia del plugin acepta ambas unidades. Además la documentación exige `data.id` en minúsculas si es alfanumérico y el SDK no lo hace: el plugin lo pasa en minúsculas al `WebhookSignatureValidator`.                                                                                                                                                                                                                                                            |
| DEC-10 | 2026-10-18 | Decisión nueva              | OAuth con `fetch`                                                    | El cliente `OAuth` del SDK 3.6.1 no soporta PKCE (`code_verifier`, `code_challenge`), `grant_type` ni `test_token` en sus tipos. Se usa `fetch` nativo contra `/oauth/token` (plan B del PRD 16.5). El SDK se usa para preferencias, pagos, reembolsos, cancelaciones y firma.                                                                                                                                                                                                                                                                                                                                     |
| DEC-11 | 2026-10-18 | Observación                 | Documentación de renovación                                          | La guía de renovación solo documenta `access_token` y `refresh_token` en la respuesta, y menciona `authorization_code` en el texto pero no en el ejemplo. Se envía solo `refresh_token` (como en el ejemplo) y, si falta `expires_in`, se asume 180 días (vigencia documentada). A confirmar en sandbox.                                                                                                                                                                                                                                                                                                           |
| DEC-12 | 2026-10-18 | Decisión nueva              | `module: nodenext` en servidor y plugin                              | NestJS 12 se publica solo como ESM y TypeScript 5.8 solo permite `require()` de ESM con `module: nodenext`. Ambos paquetes usan `nodenext` (salida CommonJS, sin `type: module`). Node 24 carga el ESM de Nest con `require()` sin problemas (servidor y worker arrancan).                                                                                                                                                                                                                                                                                                                                         |
| DEC-13 | 2026-10-18 | Decisión nueva              | El handler vuelve a verificar el pago                                | `addPaymentToOrder` es una mutación pública de la Shop API: cualquier comprador podría llamarla con un `mpPaymentId` inventado. `createPayment` consulta el pago a Mercado Pago con el token del local y exige estado `approved`, `external_reference` igual al código del pedido, ARS y monto exacto. Sin un pago aprobado real de ese pedido no hay forma de liquidarlo desde el frontend. Cuesta una segunda consulta por pago aprobado.                                                                                                                                                                        |
| DEC-14 | 2026-10-18 | Decisión nueva              | Idempotencia con tabla de reclamos y bloqueo por pedido              | Entidad `MercadoPagoPaymentClaim` con índice único por `mpPaymentId` (estados `recorded`, `processing`, `settled`, `needs_review`): solo quien gana el reclamo agrega el pago, y un reclamo `processing` abandonado se puede retomar a los 5 minutos. Además, en PostgreSQL cada liquidación toma `pg_advisory_xact_lock` sobre el pedido: sin él, dos pagos aprobados distintos para un mismo pedido se agregaban los dos (verificado quitando el bloqueo en `e2e/concurrency.e2e-spec.ts`). El segundo queda en `needs_review` y se avisa al local.                                                              |
| DEC-15 | 2026-10-18 | Decisión nueva              | Las `back_urls` se validan contra el canal                           | El PRD no dice quién decide el dominio de retorno. Un campo propio del Channel, `mpStorefrontUrl` (solo editable por el superadmin, no público), fija el origen de la tienda; `createMercadoPagoCheckout` exige https, no local (regla de Mercado Pago) y del mismo origen. Así un comprador nunca es enviado a un dominio que el local no configuró. El script de alta (T6) lo completa.                                                                                                                                                                                                                          |
| DEC-16 | 2026-10-18 | Decisión nueva              | `mp-connect` sin confiar en el cuerpo                                | La documentación no describe el cuerpo de las notificaciones `mp-connect`. Al recibir una, el plugin comprueba con Mercado Pago (`GET /users/me` con el token del local, y renovación si falla) si el acceso sigue vigente y solo marca `disconnected` si de verdad fue revocado. Misma regla que para los pagos: la notificación no es la fuente de verdad. A confirmar en sandbox qué trae el cuerpo.                                                                                                                                                                                                            |
| DEC-17 | 2026-10-18 | Decisión nueva              | Reembolso rechazado = reembolso `Failed` con mensaje                 | Si Mercado Pago rechaza el reembolso (por ejemplo, sin saldo), `createRefund` devuelve `state: 'Failed'` con `metadata.errorMessage` con el motivo de Mercado Pago, en lugar de lanzar una excepción: queda el intento registrado en el pedido. Falta confirmar en el dashboard cómo se muestra `metadata` (T3, extensión del dashboard).                                                                                                                                                                                                                                                                          |
| DEC-18 | 2026-10-18 | Decisión nueva              | Mutación `cancelMercadoPagoPayment`                                  | Vendure solo ofrece `cancelPayment` para pagos que él conoce, y este plugin nunca registra pagos pendientes (el PRD 9.8 manda no agregarlos). Para cumplir "cancelaciones desde el panel" (PRD 9.9) se agrega una mutación de la Admin API (permiso `UpdateOrder`) que cancela un pago `pending` o `in_process` del propio canal y deja una nota en el pedido. El `cancelPayment` del handler queda implementado igual.                                                                                                                                                                                            |
| DEC-19 | 2026-10-18 | Decisión nueva              | Clave de idempotencia y vigencia alineadas                           | La clave de idempotencia de la preferencia es el hash de (canal, pedido, total, URLs, ventana de 5 min) y `expiration_date_from/to` se calculan desde el inicio de esa misma ventana, para que repetir la llamada dentro de la ventana envíe un cuerpo idéntico. Efecto: la vigencia real es entre 25 y 30 minutos. A confirmar en sandbox que Mercado Pago acepta un `expiration_date_from` unos minutos en el pasado.                                                                                                                                                                                            |
| DEC-20 | 2026-10-18 | Decisión nueva              | `syncMercadoPagoPayment` no exige la sesión del comprador            | El comprador vuelve de Mercado Pago a veces sin su sesión original. La mutación solo recibe un puntero (`paymentId`) y aplica las mismas reglas que el webhook: consulta con el token del local, referencia, moneda y monto exactos, idempotencia. Sin un pago aprobado real de ese pedido no puede cambiar nada; devuelve únicamente el estado del pedido cuyo código ya conoce quien llama.                                                                                                                                                                                                                      |
| DEC-21 | 2026-10-18 | Decisión nueva              | `ErrorCode` extendido                                                | Los errores propios (`MercadoPagoError`) necesitan `extend enum ErrorCode { MERCADOPAGO_ERROR }`: Vendure 3.8 no agrega los códigos de errores propios al enum.                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| DEC-22 | 2026-10-18 | Decisión nueva              | Rol del dueño sin `ReadSettings`, `ReadChannel` ni `ReadSeller`      | Las consultas `channels` y `sellers` de la Admin API no filtran por canal: con esos permisos un dueño vería nombre, CUIT, contacto y token de todos los demás locales (verificado con una prueba). El rol del dueño tiene los permisos concretos que necesita (catálogo, pedidos, clientes, envíos, stock, zonas e impuestos de solo lectura, `ManageMercadoPago`). El dashboard conoce el canal del usuario por `me { channels }` y `activeChannel`, que no piden permiso. Los datos del local (CUIT, contacto, logo) los edita el superadmin. A confirmar con una prueba manual del dashboard (VERIFICATION.md). |
| DEC-23 | 2026-10-18 | Decisión nueva              | Canal por defecto en ARS y español                                   | El PRD 5.2 supone que todos los canales usan ARS para que el precio replicado en el canal por defecto no genere incoherencias. `BaseDataService` alinea el canal por defecto (ARS, es, IVA incluido, zona Argentina) al arrancar, además de crear Argentina, su zona y el IVA 21 % si faltan. Es idempotente.                                                                                                                                                                                                                                                                                                      |
| DEC-24 | 2026-10-18 | Decisión nueva              | Tarifa de envío: `includesTax: include` con IVA 0                    | La tarifa fija es lo que paga el comprador, con impuestos incluidos. Con el calculator por defecto y esos argumentos el precio con impuestos es exactamente la tarifa configurada para cualquier pedido (resuelve V8, con prueba). El método de envío con tarifa usa un checker propio (`delivery-zone-eligibility-checker`: país del domicilio y monto mínimo), porque Vendure no trae uno por zona.                                                                                                                                                                                                              |
| DEC-25 | 2026-10-18 | Decisión nueva              | Alta atómica con asignación a canal posterior                        | `provisionStore` corre en una sola transacción con el contexto del superadmin: crea Seller, Channel, Role, Administrator, StockLocation, dos ShippingMethod y PaymentMethod, y luego los asigna al canal del local. Si falla cualquier paso (por ejemplo, email de administrador repetido) no queda nada. Los scripts usan el mismo servicio con un contexto de superadmin real, porque crear un rol exige que quien lo crea tenga esos permisos.                                                                                                                                                                  |
| DEC-26 | 2026-10-18 | Observación                 | Consultas de listas sin `take`                                       | `HardenPlugin` (`maxQueryComplexity: 500`) rechaza con "Query is too complex" una lista sin `take` explícito. `commerce-core` y la tienda de referencia siempre lo envían.                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| DEC-27 | 2026-10-18 | Decisión nueva              | Leer el propio pedido por código durante el pago                     | Con la estrategia por defecto de Vendure un invitado solo puede leer un pedido por código **después** de colocado, no mientras está en `ArrangingPayment`; la pantalla de resultado no podría consultar el estado. El plugin envuelve la estrategia configurada (`SessionOrderByCodeAccessStrategy`) y permite además leer el pedido activo de la propia sesión. Otra sesión sigue sin poder leerlo (probado).                                                                                                                                                                                                     |
| DEC-28 | 2026-10-18 | Decisión nueva              | `commerce-core`: sesión como adaptador                               | El token de sesión del comprador (`vendure-auth-token`) se guarda en un `SessionStore` que inyecta cada frontend (cookie httpOnly en Next.js, memoria en pruebas). El paquete no lee variables de entorno, no importa módulos de Node ni el SDK de Mercado Pago, y una prueba lo verifica sobre el código fuente y las dependencias. `waitForPayment` no acepta el estado de la redirección como dato: el `paymentId` es solo un puntero para `syncMercadoPagoPayment`.                                                                                                                                            |
| DEC-29 | 2026-10-18 | Decisión nueva              | Esquema de la Shop API versionado                                    | `packages/commerce-core/schema.shop.graphql` es una instantánea del esquema (con las mutaciones del plugin). `npm run codegen` corre sin servidor; `npm run schema:update` la refresca desde un servidor con `APP_ENV=dev`. Los tipos generados (`src/gql`) también se versionan.                                                                                                                                                                                                                                                                                                                                  |
| DEC-30 | 2026-10-18 | Decisión nueva              | Tienda de referencia: idioma y diseño                                | Los textos de la interfaz de la tienda de referencia están en español neutro: es la lengua de quienes compran (Argentina, ARS) y del PRD. Diseño simple y neutro con Tailwind 4, sin marca. El nombre de la cuenta compartida es configurable (`PLATFORM_NAME`, por defecto "la plataforma") para cumplir PRD 6.3 sin atar el proyecto a ninguna marca.                                                                                                                                                                                                                                                            |
| DEC-31 | 2026-10-18 | Decisión nueva              | Tienda de referencia: arquitectura                                   | Todas las llamadas a la Shop API salen del servidor de Next.js (Server Components, Server Actions y una ruta de estado de pago); la sesión del comprador vive en una cookie httpOnly. Al iniciar se comprueba que el token no sea el del canal por defecto (PRD 5.2). La configuración se lee en cada request (no en el build) para que una misma imagen sirva a cualquier local. La pantalla de resultado no lee `status` de la URL: solo usa `payment_id` y `external_reference` como punteros.                                                                                                                  |
| DEC-32 | 2026-10-18 | Decisión nueva              | Opción `allowInsecureReturnUrls`                                     | Solo para pruebas y demos locales: acepta URLs de retorno `http`/locales en el origen configurado del local, porque la prueba E2E corre en `localhost`. Por defecto está apagada y las URLs https no locales siguen siendo obligatorias (Mercado Pago tampoco acepta otras). Variable: `MP_ALLOW_INSECURE_RETURN_URLS`.                                                                                                                                                                                                                                                                                            |
| DEC-33 | 2026-10-18 | Decisión nueva              | Pruebas E2E de la tienda con un backend real y Mercado Pago simulado | `npm run test:e2e -w @tiendasaas/storefront-reference` levanta Vendure (SQL.js, plugins reales, local dado de alta con el mismo servicio que el script), un simulador de la API de Mercado Pago (msw) y una página de pago simulada que redirige como la real (`payment_id`, `status`, `external_reference`) con cinco escenarios: aprobado con webhook, aprobado sin webhook, rechazado, pendiente y "la URL dice aprobado pero el pago está pendiente". Las pruebas con la cuenta de sandbox real siguen siendo manuales (VERIFICATION.md).                                                                      |
